# Task Manager API

REST API for task management, implemented with NestJS, TypeORM and PostgreSQL.

## Requirements

- Node.js 20+
- npm 10+
- Docker / Docker Compose (or a PostgreSQL 13+ instance)

## Quick start

```bash
cp .env.example .env
docker compose up -d postgres
npm install
npm run migration:run
npm run start:dev
```

The API is available at `http://localhost:3000/api/v1`.

For production, configure the database connection through environment variables and run `npm run build` followed by `npm run start:prod`. Database schema synchronization is deliberately disabled; schema changes must go through reviewed migrations.

## Environment variables

| Variable | Default | Description |
| --- | --- | --- |
| PORT | 3000 | HTTP port |
| API_PREFIX | api/v1 | Global route prefix |
| DATABASE_HOST | localhost | PostgreSQL host |
| DATABASE_PORT | 5432 | PostgreSQL port |
| DATABASE_USER | postgres | Database user |
| DATABASE_PASSWORD | postgres | Database password |
| DATABASE_NAME | task_manager | Database name |
| DATABASE_URL | empty | Optional full connection URL |
| DATABASE_SSL | false | Enable TLS (managed DBs) |

When `DATABASE_URL` is set it takes precedence over the individual connection fields. Never commit a real `.env` file.

## Data model

A task contains:
- `id`: UUID generated by PostgreSQL.
- `title`: required string, up to 160 characters.
- `description`: optional text.
- `status`: `pending`, `in_progress`, or `done` (defaults to `pending`).
- `responsible`: required email address.
- `dueDate`: required ISO 8601 date.
- `createdAt` and `updatedAt`: server-managed timestamps.

## REST endpoints

All endpoints are under `/api/v1/tasks`.

| Method | Path | Description | Success |
| --- | --- | --- | --- |
| POST | /tasks | Create a task | 201 |
| GET | /tasks | List tasks | 200 |
| GET | /tasks/:id | Get one task | 200 |
| PATCH | /tasks/:id | Update a task | 200 |
| DELETE | /tasks/:id | Delete a task | 204 |

### List filters and pagination

`GET /api/v1/tasks?status=in_progress&responsible=person@example.com&page=1&limit=20`

- `status`: optional enum filter.
- `responsible`: optional exact, case-insensitive email filter.
- `page`: 1-based page number (default 1).
- `limit`: page size (default 20, maximum 100).

List response:

```json
{
  "items": [],
  "total": 0,
  "page": 1,
  "limit": 20,
  "totalPages": 0
}
```

### Example create request

```http
POST /api/v1/tasks
Content-Type: application/json

{
  "title": "Prepare release",
  "description": "Review and publish the next version",
  "responsible": "person@example.com",
  "dueDate": "2026-12-01",
  "status": "pending"
}
```

## Validation and errors

The global validation pipe rejects unknown fields, validates DTO constraints and converts query parameters. Invalid input returns HTTP 400. Invalid UUID path parameters return 400; missing tasks return 404. NestJS standard exception handling provides structured error responses. Delete returns 204 without a response body.

## Migrations

```bash
npm run migration:run
npm run migration:revert
```

Generate a migration after changing entities:

```bash
npm run migration:generate
```

Review generated SQL before applying it. The initial migration creates the task table, enum and indexes.

## Architecture

- **models**: TypeORM entity and domain status enum.
- **validations**: request DTOs and class-validator constraints.
- **repositories**: persistence contract and PostgreSQL/TypeORM adapter.
- **services**: application rules and not-found handling.
- **controllers**: HTTP routes, parameter parsing and status codes.
- **serializers**: explicit public response representation.
- **interceptors**: response serialization boundary.
- **database**: TypeORM configuration and versioned migrations.

The repository contract is injected through a token so business services can be tested without PostgreSQL. The API deliberately has no user/authentication module because the requested scope defines a responsible field but no identity lifecycle or authorization rules.

## Tests

Run unit tests with `npm test`, coverage with `npm run test:cov`, and HTTP-level tests with `npm run test:e2e`. Tests are kept in a dedicated commit after the implementation commits.

## Decisions and possible improvements

- PostgreSQL was selected for production-grade relational persistence and native UUID/enum support.
- TypeORM migrations are used instead of `synchronize` to make schema changes explicit and deployable.
- Pagination is bounded to 100 records per request; results are sorted newest first with a stable UUID tie-breaker.
- Responsible is represented as an email string. If the product later introduces users, this can become a foreign key with authorization and assignment history.
- With more time: add authentication/authorization, audit history, soft deletion, optimistic concurrency, OpenAPI/Swagger, structured logging, rate limiting, and CI against a disposable PostgreSQL service.

## Use of AI

AI assistance was used to scaffold the architecture, propose DTO constraints, repository/service boundaries, migration and tests. The generated suggestions were reviewed and adapted to the requested NestJS + TypeORM + PostgreSQL stack, including keeping database synchronization disabled, using a repository interface for isolated service tests, enforcing bounded pagination, and documenting the responsible field as an email. The implementation and test suite should still be run in the target environment before deployment.
